# Перенос открытия в s22: самостоятельный этап после 0.9.14

**Реализовано 06.10.2026** по этому проекту (`src/story.js`: `fifthOpening/pendingOpening/deferOpening/deferView`; `src/data/story.js`: триггер s22). Проверка — `node sim/defer-open.js`. Ниже — исходный проект решения.

## Что сейчас происходит

`src/data/story.js`, сцена `s22`, вариант 0 обещает перенос открытия пятой точки на три дня, но одновременно говорит «на понедельник» после воскресенья. Эти календарные утверждения несовместимы. Эффект `deferOpen` в `src/story.js` только кладёт `{kind:'deferOpen',days:3,day:S.day}` в очередь. Обработчик очереди узнаёт `scene`, `rivalNear`, `journal`; неизвестную запись удаляет. Дата открытия не меняется.

Есть второй дефект предпосылки: `trigger.any` сейчас проверяет `stores:5` или 24 месяца. `cond.stores` считает **уже открытые** точки. Значит, этот путь приходит после открытия пятой; месячный путь вообще не гарантирует открывающейся точки. Исправлять эффект выбором случайной точки или переносом всех `opening` нельзя: это не соответствует обещанию и меняет посторонние проекты.

`Engine.tick` сначала увеличивает день, затем `dailyStores` переводит `opening` в `open` при `S.day >= openDay`, потом `dailyStaff` принимает `incoming`. Story.day обёртка вызывается **после** движка. Поэтому обработчик переноса в Story.day опоздал бы, если точка открывается на этом tick. Перенос необходимо применять непосредственно во время `Story.resolve`, до следующего Engine.tick.

## Конкретный объект и поведение

Переносить только одну ещё не открывшуюся точку **№5** в городе показанной сцены, по стабильному `store.id`. Цехи, точки №4/№6, открытые точки и другие города не затрагивать. Не выбирать «любую следующую» как запасной вариант. Номер соответствует номеру из реальной аренды (`Engine.rentStore` назначает `num`), а не позиции в массиве: после закрытия точки позиции уже не совпадают.

При постановке `s22` зафиксировать в `R.pending.deferOpening` `{city,storeId}`. Если подходящей пятой нет — фиксировать `storeId:null`. Это не даёт уже показанному окну незаметно переключиться на другое помещение после смены города, аренды или загрузки. Дополнительное поле pending необязательно для старых сохранений; их незавершённый s22 получает цель из текущего реального состояния при показе/ответе.

Если пятой открывающейся нет, показать честный альтернативный разговор про ужин без заявления об открытии и простое. Варианты остаются с теми же индексами и семейными последствиями; перенос становится явным no-op. Не заводить «кредит переноса», который затронет случайную будущую аренду. Если выбранная цель успела открыться/исчезнуть либо активный город изменился, график также не менять: показанный текст при повторной отрисовке становится нейтральным.

Новое открытие: `oldOpenDay + 3`. `incoming[i].day = max(oldIncomingDay,newOpenDay)` только этой точки. Начальный штат, нанятый на открытие, сдвигается вместе с ним; отдельный более поздний найм сохраняет свой реальный срок. Даты сотрудников нельзя всем безусловно увеличивать на три: это задержало бы независимый будущий найм. Если агрегатор включён или дата его подключения уже задана, `aggDay = max(oldAggDay,newOpenDay)`: разгон начинается не раньше запуска, уже запланированное более позднее подключение не ускоряется.

Не менять `rentPaidUntil`, аренду, зарплаты, capex, количество найма, RNG, `openedDay`, другие ограничения `closedUntil/repairUntil`. Перенос не возвращает расходы и не дарит продление оплаченного календарного срока аренды. Точка остаётся `opening`, и неизменный движок открывает её в новую дату. Порядок `dailyStores → dailyStaff` и отсутствие продавцов в первый расчёт открытия являются существующим поведением движка; его не следует попутно менять этим исправлением.

## Предлагаемый код

Добавить в Story чистый поиск и отдельную применяющую функцию. Имена полей — предложение для небольшого патча; это не изменение существующего schema version.

```js
function openingCity(S) {
  return (S.corp && S.corp.active) || 'ufa';
}
function fifthOpening(S, ref) {
  if (!S) return null;
  const city = openingCity(S);
  if (ref && (ref.city !== city || !ref.storeId)) return null;
  const list = (S.stores || []).filter(st =>
    st.num === 5 && st.status === 'opening' &&
    Number.isFinite(st.openDay) && st.openDay > S.day &&
    (!ref || st.id === ref.storeId));
  // Не угадывать цель повреждённого/нестандартного сохранения с повторным номером.
  return list.length === 1 ? list[0] : null;
}
function pendingOpening(S, R) {
  const p = R && R.pending;
  const ref = p && p.id === 's22' && p.deferOpening;
  return fifthOpening(S, ref || null);
}
function deferOpening(S, R, days) {
  const st = pendingOpening(S, R);
  const n = Math.max(0, Math.round(Number(days) || 0));
  if (!st || !n) return null;
  const next = st.openDay + n;
  st.openDay = next;
  for (const hire of st.incoming || []) {
    if (Number.isFinite(hire.day)) hire.day = Math.max(hire.day, next);
  }
  if (st.agg || st.aggDay != null) {
    st.aggDay = Math.max(Number.isFinite(st.aggDay) ? st.aggDay : next, next);
  }
  return `Открытие №${st.num}: ${E().fmtDate(next)} (${n} дн. позже)`;
}
```

В `start`, после принятого `R.pending` и до уведомления, только для `s22`:

```js
if (sc.id === 's22') {
  const st = fifthOpening(S, null);
  R.pending.deferOpening = {city:openingCity(S), storeId:st ? st.id : null};
}
```

В `apply` заменить постановку неработающей записи очереди:

```js
case 'deferOpen': return deferOpening(S, R, fx.days || 3);
```

Для естественного появления перед запуском пятой добавить условие `openingStoreNum` в `cond` (сейчас нужен только номер 5; не расширять значение на любые проекты):

```js
if (c.openingStoreNum != null) {
  return c.openingStoreNum === 5 && !!fifthOpening(S, null);
}
```

Триггер `s22` дополнить, сохраняя прежние открытые/временные альтернативы для нейтрального семейного разговора:

```js
trigger: {after:['s21'], any:[
  {openingStoreNum:5}, {stores:5}, {months:24}
]}
```

Уточнить реплики и выборы. Для реальной цели: «Скоро открытие пятой. …», вариант 0 «Сдвину открытие пятой точки на три дня.», стоимость «открытие №5 на 3 дня позже», описание без обещания фиксированной денежной суммы. Вариант 1 «Открою по плану. Потом отпразднуем.» Календарь показывает `E.fmtDate(oldOpenDay)` и новую дату, а не выдуманное воскресенье/понедельник.

Для отсутствующей цели: «Пекарни работают, а семья всё ждёт тебя за столом.»; вариант 0 «Приеду на семейный ужин.», описание «Семья рядом. График открытий не меняется.», `cost:null`; вариант 1 «Сегодня останусь с делами. Потом отпразднуем.» Нейтральные family/care эффекты уже соответствуют этим двум решениям. Обе презентации должны получать **тот же** `pendingOpening` что и применяющая функция, без RNG и без изменения definitions. `sceneView` сейчас меняет только lines/title: небольшой патч должен явно разрешить только поля представления choice (`label/desc/cost`), сохраняя id, порядок, need, effects и log контракты. Не изменять shared `BK.STORY.scenes` при рендере.

Пример специальной презентации внутри `sceneView`: существующее окончательное `return Object.assign(...)` заменить на `const view = Object.assign(...)`; затем применить следующий блок и вернуть `view` для других сцен. Это не общий механизм переписывания эффектов:

```js
if (sc.id === 's22') {
  const st = pendingOpening(S, R);
  const choices = sc.choices.map((ch, i) => Object.assign({}, ch,
    i === 0 ? {
      label: st ? 'Сдвину открытие пятой точки на три дня.' : 'Приеду на семейный ужин.',
      desc: st ? 'Открытие №5 на три дня позже. Семья рядом.'
               : 'Семья рядом. График открытий не меняется.',
      cost: st ? 'открытие №5 на 3 дня позже' : null,
    } : {label: st ? 'Открою по плану. Потом отпразднуем.'
                   : 'Сегодня останусь с делами. Потом отпразднуем.'}));
  const lines = view.lines.map(l => l.who !== 'gulya' ? l :
    Object.assign({}, l, {text: st
      ? `Открытие пятой запланировано на ${E().fmtDate(st.openDay)}. На три дня позже — ${E().fmtDate(st.openDay + 3)}. Я не настаиваю. Просто говорю, как есть.`
      : 'Пекарни работают, а семья всё ждёт тебя за столом.'}));
  return Object.assign({}, view, {lines, choices});
}
return view;
```

`StoryUI.fxChips` сейчас безусловно показывает область «Открытие» для `deferOpen`. Одной замены `cost:null` недостаточно: при no-op этот значок тоже нужно скрыть. Добавить чистый публичный метод `deferOpeningTarget(S) { return pendingOpening(S, state(S)); }` в `BK.Story`; в существующей ветке `deferOpen` рендера добавлять impact только если `ST.deferOpeningTarget(S)` существует. У API эффекты остаются исходными: фильтровать `choices.effects` в sceneView нельзя. Это сохраняет согласованность слов, значков и действительно затронутых объектов.

Для летописи использовать честную выбранную подпись из sceneView (resolve уже записывает её), чтобы старое обещание «понедельник» не возвращалось в итогах.

## Старые записи очереди

У старой `{kind:'deferOpen',days,day}` нет storeId и города. Особенно спустя много дней она не позволяет восстановить, какая точка существовала при выборе. Не применять такой перенос задним числом к текущей пятой, не закрывать открытый магазин и не переносить новую аренду. Сохранить совместимость безопасным удалением неизвестной старой записи, как делает текущий обработчик; желательно явным `if (q.kind === 'deferOpen') return false` с комментарием о legacy no-op. Ни нового отложенного действия, ни ретроактивных выплат за исторически несработавший выбор не вводить. Старый **pending** s22, где ответ ещё не выбран, получает новое честное поведение при ответе; старый уже завершённый выбор не переигрывается.

Если позже появится отдельный отложенный перенос с идентификатором города/точки, он должен обрабатываться **до Engine.tick**, а не в текущем post-tick Story.day. Для нынешнего эффекта очередь вообще не нужна.

## Смысловая регрессия для отдельного этапа

Не запускать в текущем full runner 0.9.14. После публикации создать самостоятельный последовательный regression, затем обновить effect audit: старый oracle ожидает запись `deferOpen` в очереди и должен ожидать реальную дату конкретной точки.

1. Через настоящий `Engine.newGame`, законные `chooseProduction/rentStore` и реальное ожидание открыть четыре точки; арендовать пятую и шестую, подключить агрегатор обычным API. Достичь/показать s22 после настоящего s21; не подделывать `status`, num, openDay или incoming. Зафиксировать snapshot перед ответом.
2. Выбрать вариант 0. Только id пятой остаётся opening с `openDay+3`; исходная шестая, цех, деньги/резерв/loan/rentPaidUntil и RNG не меняются. Family +15/care +5 меняются как раньше. Начальный incoming пятой и aggDay не раньше новой даты; отдельный легально нанятый сотрудник с более поздней датой остаётся на своей дате.
3. Пройти настоящие tick до старой даты: пятая не открылась и не начала продажи/доставку; в новую дату нормальный движок открывает её и принимает начальный штат по своему существующему порядку. Шестая открывается по исходному графику, независимо от решения семьи. Не требовать от первых суток выручки выше нуля: существующий движок принимает штат после dailyStores.
4. Из реального Rewind.take до ответа восстановить копию, повторить вариант 0 и сравнить durable states/RNG. Сохранить после ответа и перезагрузить: даты не увеличиваются повторно, resolve закрытого pending отказывает без изменений.
5. Вариант 1 из того же исходного snapshot не переносит никаких дат, даёт прежние отрицательные family/care эффекты и честный текст «по плану».
6. Отдельные реальные партии с пятью уже открытыми точками и с месячным/fallback приходом s22 без opening: альтернативная презентация не заявляет потери трёх дней; вариант 0 не переносит иной магазин, не заводит queue и не расходует RNG. Если позже законно арендовать новую точку, она не наследует перенос.
7. Сохранение с legacy queue `{kind:'deferOpen',days:3,day:<старый день>}`: загрузка/следующий tick удаляет только запись, не меняя никакого чужого openDay. Можно дополнить отдельным schema fixture, явно назвав его **legacy serialization fixture**, а не игровой достижимостью. Не включать его как покрытую сюжетную ветку allBranches.
8. Для обоих полов, светлой/тёмной темы и мобильного окна проверять реальные label/cost/дату, отсутствие слова «понедельник» и подписей о переносе при отсутствии цели. Закреплённый storeId переживает сохранение; город/закрытие/пропажа цели приводят к честному no-op, а не выбору другого магазина.

Нужные решения владельца для этого исправления не выявлены: существующий вариант прямо обещает именно три дня и пятую точку. Будущий универсальный перенос всех строек или денежная компенсация за старые выборы требуют другого продуктового запроса и не входят в этот этап.
