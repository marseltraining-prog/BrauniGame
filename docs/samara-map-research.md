## Совместимость mapGen

Новая `CITY_BIG.samara` должна иметь mapGen2. `geoOf` уже возвращает старый genCityGeo при явно указанном поколении1; legacy-таблицу, генератор и его RNG не трогать. `Engine.newGame` сохраняет startMapGen для новой подробной географии; обычный `Corp.enterCity` берёт cityMapGen. `Corp.applyGlobals/useCityFor` читает сохранённые startMapGen/city.mapGen. Обложка cityPreview сознательно показывает текущую новую карту для новой партии.

Старые сохранения с отсутствующим startMapGen читаются как1; уже открытые corp.cities[id].mapGen1 должны остаться1, с прежними координатами помещений. Не делать массовую миграцию mapGen при ensure/load. Новая покупка сети в старой партии создаёт новый city-record и вправе получить актуальное поколение2; это не перемещение уже существующего города.

Подключение будущего data-файла потребуется в build и sim/load ровно как Нск; тут не внесено. Экономические диапазоны районов начинать от действующих архетипов/множителей, географию отдельно сверить от баланса: десятая зона меняет распределение предложений. Не объявлять бот-баланс неизменным без сравнения.

## buyLocal/buyChain: подтверждённый дефект и минимальная будущая правка

`src/corpev.js`, функция buyChain: новый record создаётся с hardcoded `mapGen:1`. Затем `Dir.buyStores` создаёт цех и точки внутри `Corp.withCity`; withCity монтирует город через сохранённое поколение. Поэтому новая покупка даже Казани/Екб/Нск остаётся процедурной1, тогда как обычный enterCity получает актуальную подробную2.

Минимальная совместимая замена только в создании НОВОГО record:

```js
mapGen: BK.cityMapGen ? BK.cityMapGen(id) : 1
```

Это тот же контракт, что в `src/corp.js` enterCity. Поле задаётся ДО вызова buyStores, поэтому новые координаты цеха/точек соответствуют новой карте. Seed/RNG, цена, количество точек, остальные эффекты сделки не менять. Уже существующие city-records этой функцией не пересоздаются (`cr.cities[id]` проверяется в начале); загрузка и старые купленные города остаются нетронутыми. Никакой правки не внесено.

При реализации нужны смысловые проверки: новая покупка detailedcity2; новая покупка недетализированногоcity1; legacyкупленныйcity1 после save/load всёещё1 и те же координаты; buyStorespackeddistricts принадлежат выбранной карте; активныйгород и глобальная география восстановлены после withCity. Не подменять эти проверки прямым ручным созданием record — пройти реальный CorpEv.apply/resolve эффект сделки.

## Следующий конкретный проход после публикации14

Сохранить эталон Самары1, уточнить перечисленные географические пробелы по первичной карте, создать отдельный data-модуль2. Затем проверить силуэт/берега/мосты/районы/POI и старые сохранения; только после — последовательные симуляции/QA/сборка и выпуск следующей beta. Desktop обновлять после публикации по действующему правилу проекта.
