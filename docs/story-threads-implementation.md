# Сквозные линии: изолированная реализация

04.10.2026. Подготовлено для сюжетного выпуска **после 0.9.12**. Реальные
`src`, build/config, PLAN/HANDOFF не изменены этим помощником. Все игровые
правки находятся в `tmp/story-depth/threads/`. Это подготовка, не публикация
и не завершение пункта «Глубина сюжета».

## Файлы и безопасное применение

- `tmp/story-depth/threads/src/story.js`: общая подача условных реплик, фиксация
  партнёра и две конкретные починки perks.
- `tmp/story-depth/threads/src/data/story-bridges.js`: только LINE_SCENES
  `kd2/kd3/kf3/kf4`, без b-мостиков и изменения темпа.
- `tmp/story-depth/threads/src/data/story-russia.js`: только текст `gulyaBoard/s44`,
  `s4m1/sf1b/sf2`, без family и deep `s4g*`.
- `tmp/story-depth/threads/threads.patch`: diff к реальным исходникам с путями
  `a/src/...` / `b/src/...`; `manifest.json` содержит SHA-256 базы и копий.
- `tmp/story-depth/threads/static-check.js`: проверка определений данных без Engine.

Другие помощники редактируют собственные копии story-russia/bridges. Нельзя
копировать наш полный файл поверх их результата: применять непересекающиеся
hunks, предварительно `git apply --check tmp/story-depth/threads/threads.patch`.
Каталог tmp/story-depth теперь игнорируется Git; замороженный patch и manifest
сохранены для передачи в `docs/story-depth-patches/`. Документы могут войти в передачу работы отдельно;
исходники сюжетного выпуска применять только после фиксации карты.

## Что реализовано

1. **Условные реплики без нового дерева.** `sceneView(S, sc)` выбирает `views`
   сцены/реплики по существующему `cond`. Возвращает копию с другими lines/title,
   не меняет исходный BK.STORY, порядок вариантов, их эффекты или id. И UI,
   и resolve используют тот же pendingScene. Требуется копия src/story.js
   одновременно с новыми данными: старый движок игнорирует views.

2. **Рашид после `s4m1`.** `kd2/kd3` дают Гуле/Семёну старую записку и память
   вместо живого наставника. Признание Дамира в журнале/нити больше не обязано
   происходить «при Рашиде». `sf1b` показывает лист из тетради; живой вариант
   совета закрыт `noFlag:rashidGone` (и при уходе Гули к сопернику). Основные
   варианты слияния сохранены. `s4m1` журнал мягкий и не утверждает, что игрок
   получил закваску, если `s36` не случился/банку отложили.

3. **Расследование Дамира достижимо.** У второго варианта `kd2` снято требование
   стёртого в `kd1` shadow. Игрок может найти Айрата независимо от найма/отказа;
   цена 120 тыс., последствия, сроки и запись trusted прежние. Пролог не
   определяет исход навсегда. Нейтральный вариант `kd3` закрывается флагом
   `lineDamir:worker` и `damirStep:3`, без изменения счётчика warm/cold.
   Обещание ещё одной встречи через год снято; на тёплом последнем ужине
   Семён вспоминает ключи от его смены.

4. **Партнёр сохраняет личность.** Расчёт продолжается для none/пустого значения,
   но уже записанный helper/tyrant не пересчитывается до kf3. Пороги и score
   прежние; старый сохранённый тип сохраняется. `kf4` при `mateWork:no` говорит
   о несостоявшемся общем деле вместо двух начальников; варианты/эффекты прежние.
   В `kf3` уточнён размер вложения: два процента выручки **прошлого месяца**,
   минимум 20 тыс. ₽ (`engine.js: cash.revPct * max(lastMonthRev, 1e6)`).

5. **Конкретные обещания perks.** givePerk передаёт additive loyalty через
   обычный Engine.applyEffects: kinNear/kinFar действительно дают ±2 настроения
   один раз при выборе сцены, вместо модификатора с отсутствующим m. Число взято
   из исходных данных, новых финансовых бонусов нет. twocrusts повторно не
   выдаётся на совете, если получен при соглашении. Старые уже двойные бонусы
   не удаляются задним числом. Ежегодное выращивание директора gulyaBoard
   заменено честной формулировкой совета; реальный ежегодный найм не добавлен.

6. **Финал и судьба Гули.** На совете own говорит как поставщик, poached
   представляет Олег; игроку не сообщают, что она всё ещё начальник его цеха.
   `sf2` при cold открывается деловым ужином Семёна в офисе, а не безусловно
   тёплым семейным столом. Концовки, требования выбора и их экономические эффекты
   сохранены. Это первые конкретные отдачи, не полная матрица всех персонажей.

## Что проверено локально

`node --check` для всех трёх копий: успешно. Статическая проверка определений:
**78 сцен, 172 варианта**, ids/порядок, триггеры, fallback, queueOnly, form/ch,
финансовые эффекты и расписание прежние. Разрешённые исключения явно проверены:
флаги нейтрального kd3, текст журнала s4m1 и признания kd2, вход расследования
kd2, защита живого совета sf1b. Проверка сначала выявила ожидаемое изменение
текста нити kd2; сравнение уточнено до нетекстовых полей только этого варианта.

Ни Engine.tick, ни бот, ни браузер, ни release runner не запускались. Проверка
определений выполняет только файлы данных в VM и сравнивает их структуры;
это **не** доказательство игрового темпа/баланса/покрытия ветвей.

## Проверки после применения, строго последовательно

- Загрузить helper/tyrant до kf3; изменить характер: тип остаётся прежним.
  none может определиться позже. Сохранение/загрузка не меняют тип.
- Каждый путь kd1 открывает расследование kd2; расходы ровно 120 тыс.;
  neutral kd3 пишет worker и не увеличивает warm/cold. Старые состояния
  served/close/shadow продолжают иметь законный следующий выбор.
- rashidGone перед kd2/kd3/sf1b: только память/записка, живой совет недоступен;
  без флага обычные реплики сохранены. После ухода Гули нет утверждения, что
  она руководит вашим цехом. Загруженное открытое окно корректно выбирает view.
- `mateWork:no` не даёт второго начальника; холодный последний ужин не
  объявляет семейную близость фактом. Одинаковые индексы выбора до/после view.
- kinNear/kinFar дают ±2 один раз; повторная выдача twocrusts не добавляет
  модификатор. Старый сохранённый двойной perk не вызывает новую выдачу.
- Полный baseline/боты/сюжетные ветви и UI 1440/390/360 в обеих темах,
  Chromium/WebKit — после общей интеграции. Эти механические изменения
  отделить от чистой вычитки: нельзя заявить неизменность всех состояний.

## Остаток аудита

Не реализованы: обещанный визит kf1, уникальные ключи счётчика закрытых линий,
настоящий кризис-зависимость от денег партнёра, реальное слияние объектов Corp,
назначение реального директора Дамира, полная персональная память каждого
финала и всех месячных реплик. Не добавлять их автоматически в первую волну.

Копии и patch заморожены после передачи родителю/координатору. Для дальнейших
правок сначала согласовать владельца файла, чтобы не смешать независимые копии.

## Подготовленный интеграционный тест (не запускался)

По дополнительному поручению родителя написан
`tmp/story-depth/tests/sim/story-depth.js`. Применённый замороженный patch теперь
архивируется в `docs/story-depth-patches/threads.patch`; временные копии
игнорируются Git. Тест **не запускался**, в том числе не подключался к runner 0.9.12.

После объединения сюжетных фрагментов запуск из корня:

```sh
node tmp/story-depth/tests/sim/story-depth.js
```

Если файл перенесён в реальные проверки как `sim/story-depth.js`, команда —
`node sim/story-depth.js`. Он выбирает корень по расположению и загружает
актуальный `sim/load.js`; подмены Engine/Story нет. Пока patch не применён,
проверка требует наличие `Story.sceneView` и намеренно останавливается.

Проверяются реальные start/pending/resolve и сериализация Rewind.take с
последующим восстановлением Story/Threads/городских globals: helper/tyrant после
смены поведения и загрузки, появление человека после none; все законные варианты
kd1 из owe/shadow, расследование за 120 тыс. и переход к boss; neutral kd3 без
нового warm/cold; rashidGone в kd2/kd3/sf1b, положительный живой совет и отсутствие
Гули; реальный отказ kf3→kf4; ровно одно начисление kin ±2; одно twocrusts при
соглашении и совете, включая загрузку. Индексы вариантов проверяются по кнопкам
реального StoryUI.renderer и по результату resolve; shared BK.STORY не мутирует.

Минимальный document adapter только предотвращает DOM-ready boot и позволяет
получить HTML настоящего StoryUI. Условия доступности не переписаны в тесте:
disabled читается из сгенерированной кнопки. Это не браузерная проверка макета.
Прямые состояния служат небольшими фикстурами конкретной ошибки; фактические
триггеры kd2/kd3/kf4 проверяются отдельно. Прогон всей игры, темп и баланс
по-прежнему требуют последовательных ботов и браузера после интеграции.
